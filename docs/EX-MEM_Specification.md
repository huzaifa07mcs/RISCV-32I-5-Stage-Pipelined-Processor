# EX/MEM Pipeline Register Specification

## 1. Module Name
`EX_MEM`

## 2. Purpose
The EX/MEM Pipeline Register separates the **Execute (EX)** stage from the **Memory Access (MEM)** stage in the pipelined RV32I processor. It captures all outputs generated by the Execute stage on every rising edge of the clock and forwards them to the Memory stage during the next clock cycle.

This register stores the ALU result, data to be written into memory, destination register information, PC+4 (for JAL write-back), and the control signals required by the MEM and WB stages.

**Design note:** Branch resolution (`Zero` flag evaluation, branch-taken decision, and any resulting flush) happens combinationally within the EX stage itself, *before* this register — not carried forward into MEM. This keeps the branch misprediction penalty at 2 cycles (flushing IF/ID and ID/EX) rather than 3. `branch_target` and `zero` are therefore **not** part of this register's interface.

## 3. Inputs

| Signal | Width | Description |
|---------|:----:|-------------|
| clk | 1 | System clock |
| reset | 1 | Active-high synchronous reset |
| flush | 1 | Clears pipeline register when asserted |
| alu_result_in | 32 | ALU computation result |
| rs2_data_in | 32 | Register data to be written into Data Memory (SW) |
| rd_in | 5 | Destination register address |
| pc_plus4_in | 32 | PC+4 — needed for JAL's write-back value in WB stage |
| Jump_in | 1 | Jump control signal — needed for WB-stage write-back override mux |
| MemRead_in | 1 | Enables memory read |
| MemWrite_in | 1 | Enables memory write |
| RegWrite_in | 1 | Enables register file write |
| MemToReg_in | 1 | Selects memory data or ALU result for write-back |

## 4. Outputs

| Signal | Width | Description |
|---------|:----:|-------------|
| alu_result_out | 32 | Registered ALU result |
| rs2_data_out | 32 | Registered data for Data Memory write |
| rd_out | 5 | Registered destination register |
| pc_plus4_out | 32 | Registered PC+4 (JAL write-back value) |
| Jump_out | 1 | Registered jump control |
| MemRead_out | 1 | Registered memory read control |
| MemWrite_out | 1 | Registered memory write control |
| RegWrite_out | 1 | Registered register write control |
| MemToReg_out | 1 | Registered memory-to-register control |

## 5. Functional Behavior

### Normal Operation
When `reset` and `flush` are not asserted, the EX/MEM pipeline register captures all Execute stage outputs on every rising edge of the clock.

```verilog
alu_result_out <= alu_result_in;
rs2_data_out   <= rs2_data_in;
rd_out         <= rd_in;
pc_plus4_out   <= pc_plus4_in;
Jump_out       <= Jump_in;
MemRead_out    <= MemRead_in;
MemWrite_out   <= MemWrite_in;
RegWrite_out   <= RegWrite_in;
MemToReg_out   <= MemToReg_in;
```

### Reset Operation
When `reset` is asserted, all pipeline register outputs are cleared.

```verilog
alu_result_out <= 32'b0;
rs2_data_out   <= 32'b0;
rd_out         <= 5'b0;
pc_plus4_out   <= 32'b0;
Jump_out       <= 1'b0;
MemRead_out    <= 1'b0;
MemWrite_out   <= 1'b0;
RegWrite_out   <= 1'b0;
MemToReg_out   <= 1'b0;
```

Reset inserts a NOP into the Memory stage.

### Flush Operation
When `flush` is asserted, the control signals are cleared so no memory access or register write occurs for the flushed instruction. Data-carrying fields (`alu_result`, `rs2_data`, `rd`, `pc_plus4`) don't strictly need clearing since they're harmless without an active control signal, but clearing them is safer/cleaner and matches the reset behavior:

```verilog
alu_result_out <= 32'b0;
rs2_data_out   <= 32'b0;
rd_out         <= 5'b0;
pc_plus4_out   <= 32'b0;
Jump_out       <= 1'b0;
MemRead_out    <= 1'b0;
MemWrite_out   <= 1'b0;
RegWrite_out   <= 1'b0;
MemToReg_out   <= 1'b0;
```

## 6. Priority
When multiple control signals occur simultaneously, the priority shall be:
1. Reset
2. Flush
3. Normal Update

```verilog
always @(posedge clk)
begin
    if (reset)
    begin
        ...
    end
    else if (flush)
    begin
        ...
    end
    else
    begin
        ...
    end
end
```

## 7. Hardware Resources
This module consists only of pipeline registers. No arithmetic, logical, or memory operation is performed inside this module.

Stored signals:
- ALU result
- rs2 register data (store data)
- Destination register (rd)
- PC+4 (JAL write-back value)
- Control signals: Jump, MemRead, MemWrite, RegWrite, MemToReg

## 8. Reset Behavior
Active-high synchronous reset. After reset:
- ALU result = 0
- Store data = 0
- Destination register = 0
- PC+4 = 0
- All control signals = 0

The pipeline contains an empty instruction (NOP).

## 9. Verification Strategy
The module should be verified using a dedicated testbench covering:
- Reset operation
- Normal pipeline update
- ALU result transfer
- Store data transfer
- Destination register transfer
- PC+4 transfer (confirm JAL's return address survives this stage correctly)
- Control signal transfer, including Jump
- Flush operation
- Multiple consecutive instruction transfers

| Test Case | Expected Result |
|-----------|-----------------|
| Normal clock | Inputs appear at outputs |
| Reset | All outputs become zero |
| Flush | All control signals (and data fields) become zero |
| JAL instruction | pc_plus4 and Jump correctly latched and transferred |
| Multiple instructions | Correct sequential transfer |

## 10. Notes
- This module creates the third pipeline boundary of the processor.
- No ALU operation occurs inside this module.
- No Data Memory operation occurs inside this module.
- `branch_target` and `zero` are deliberately **not** part of this register — branch resolution happens combinationally in EX stage, one stage earlier, keeping misprediction penalty at 2 cycles instead of 3. If this assumption is wrong for your design, this spec needs to be revised.
- The `rs2_data` signal is used only by store (`SW`) instructions.
- `pc_plus4` and `Jump` exist here solely to carry JAL's return-address write-back path through to WB stage — this mirrors the same signals already present in `ID_EX`.
